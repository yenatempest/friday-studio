# Team Lead Learnings — workspace-setup branch — 2026-05-07

Free-form notes captured during the workspace-setup interstitial implementation session. To be curated into CLAUDE.md by the `remembering-learnings` skill.

## Observations

- 2026-05-07: Multi-daemon hypothesis for `caps.*.http.fetch` "unknown session" errors is FALSE. Single atlasd, single `CapabilityHandlerRegistry` (atlas-daemon.ts:500-501). Real cause appears to be cascade session-id reuse: capability request lands after `ProcessAgentExecutor.execute()` finally-block unregisters the session. 27 incidents cluster around cascade dispatches from `routes/workspaces/index.ts:1817`. Captured as task #25.
- 2026-05-07: Stale daemon worktree gotcha — running daemon may have `cwd` pointing to a different worktree than the branch under investigation. `lsof -nP -iTCP:8080` + checking the deno PID's `cwd` is worth doing first when reproducing.
- 2026-05-07: `JSONSchemaSchema` (packages/schemas/src/json-schema.ts) silently strips unknown sub-keys like `format` because its inner `z.object` is non-strict and `format` isn't declared. Parsing `{ type: "string", format: "email" }` succeeds but the parsed entry only carries `type`. Affects task #12 (`workspace_config[key].schema` validation) — `z.fromJSONSchema(entry.schema)` won't see `format`, so email validation will silently no-op. Either extend `JSONSchemaSchema` to declare `format` or validate against the raw (unparsed) JSON Schema object.
- 2026-05-07: `applyMutation` (packages/config/src/mutations/apply.ts) uses `@std/yaml` parse+stringify which **strips all YAML comments**. The design doc (workspace-setup-interstitial § 6) assumed comments would be preserved. Every mutation route shares this gap. Captured as task #26 (writer migration to eemeli `yaml`). Implementation tasks should assert structure-only for now and leave a one-line `// applyMutation strips comments via @std/yaml — see task #26` for the next reader.
- 2026-05-07 (process): Jinju's #23 commit accidentally pulled in Po's `setWorkspaceConfigValues` import line — both teammates were editing `apps/atlasd/routes/workspaces/index.ts` concurrently. Project-wide `deno check` passed because Po's commit (which adds the export) landed seconds later. **Lesson**: when two teammates have file overlap on a hot route file, serialize them — don't run them in parallel even if their stated scopes seem disjoint. The hot-file rule (manage `apps/atlasd/routes/workspaces/index.ts` as a single-writer lane) needs to be enforced by the team lead, not negotiated by teammates from "git stash my unrelated changes".
- 2026-05-07 (process): `xargs -I {} deno check {}` triggers spurious TS2589 "type instantiation excessively deep" because each per-file invocation re-resolves the type graph from scratch and may hit the recursion limit alone. The skill's `git diff HEAD~1 --name-only | xargs deno check` pattern is unreliable. Project-wide `deno check` (no args) is the source of truth.
- 2026-05-07 (design): When a helper's callers have different dependency profiles (some can supply a Link client, some can't), split the helper rather than adding optional deps OR using an injector setter. `hasUnfilledConfigKeys(config)` (sync, no deps) for the manager layer; `resolveWorkspaceSetupRequirements(config, deps)` (async, with Link) for the daemon layer. Avoids: (a) silent-fallback hazards from "if no resolver set, assume false", (b) callers projecting types they don't need, (c) types that promise more than the function delivers when called without deps. Trade-off: manager-side gate only catches Config Requirements; Credential Requirements rely on the daemon-side gate. Layered defense, not single-source-of-truth.
- 2026-05-07 (process): A signature change to a helper (sync→async + new deps) silently broke 3 in-flight teammates' work because the old signature was still what they were coding against. Even with task dependencies set in the task graph, mid-task signature changes within an in-progress task ripple. **Lesson**: when a teammate's task involves an API change to a function others may consume, the team lead should pause downstream work or warn ahead. The `Closes #X` git trailer is too late — by then the rebase pain is already real.
- 2026-05-07 (process): Worktree contamination round 2. Luka's #6 commit (manager.ts gates) inadvertently swept in 78 lines of Almond's pending #10 work on `setup-requirements.ts` (async helper + credential detection types + `extractCredentials` plumbing). Almond's later #10 commit was reduced to just tests + mod.ts. Working-tree state is shared across in-flight teammates; `git add -p` or per-file staging is the only defense. **Lesson for the team lead**: when two teammates have any chance of touching the same file (even if their stated scopes are disjoint), instruct them explicitly to `git stash` peer changes before staging, OR serialize them. Stating "you'll work on different files" isn't a guarantee.
- 2026-05-07 (style): "Flip `private` to `protected` so a test subclass can inject" is a tempting test-seam pattern but pollutes production accessibility for a test affordance. Used by Luka in #6 (`signalRegistrars` field, `manager-setup-gate.test.ts`'s `TestableWorkspaceManager`). Cleaner alternatives: constructor-inject the dependency, mock at the boundary, or use `// @ts-expect-error` / `Reflect.set` as a localized test shim. Worth a polish-pass cleanup later.
- 2026-05-07 (frontend gotcha): The playground's typed Hono client gives you compile-time API contracts, but the **runtime data still flows through Zod schemas in `workspace-queries.ts`** that strip unknown fields by default. When the daemon adds a new response field (e.g. `requires_setup` in #7), the frontend type system says it's there but the parsed value is `undefined` until you also add the field to the corresponding `WorkspaceSummarySchema` / config schema. Caught by Patina in #20 — would have been an invisible "badge never renders" bug otherwise. **Lesson**: when a server-side task adds a response field consumed by the frontend, the consuming task must also extend the Zod summary schema. Worth flagging in any "extend list endpoint" task description going forward.
- 2026-05-07 (process): `git stash pop` after concurrent commits can re-introduce other teammates' files as "new untracked/modified" in your tree. Caught by Ferox in #12 — they stashed to verify a pre-existing test failure on a clean tree, popped after Leela's #21 + Patina's #22 had landed, and `git status` then showed Leela's `+layout.ts` as if it were Ferox's own pending change. Soft-reset and unstaged before committing. **Lesson**: after `git stash pop` in a multi-teammate worktree, check `git status` before staging anything — and prefer `git stash drop` if the stash was just a probe.
- 2026-05-07 (process, severe): `git checkout HEAD -- file` writes to the SHARED working tree and **destroys other teammates' unstaged changes**. Used by Leela in #24 to "scrub a peer's hunk before committing" — fortunately Jerry's #18 hunks were already committed (commit 870f1f9) before Leela's checkout, so no real damage. Teammates' mental model that "their working tree" is per-agent is wrong: there's one filesystem across all agents in a worktree. **Lesson, hard rule**: never use `git checkout HEAD -- file` in a multi-teammate worktree. To commit a partial diff cleanly, use `git restore --staged` + `git add -p` (preserves the working tree) or `git stash --keep-index` (saves what's not staged before committing). The team lead should also be more aggressive about serializing teammates whose tasks share a file, regardless of their stated scope disjointness.
- 2026-05-07 (process, severe): "Soft hand-off" of file lanes via `team-lead` ping-pong (e.g. "Ferox just released the lane, Leela claim it now") fails when in-flight teammates are racing the same file. During #16/#18, Leela's Edit attempts were silently overwritten by Jerry's concurrent writes; she got `File has been modified since read` errors and had to retry twice. **Lesson**: file-lane discipline needs a hard serialization signal, not a soft one. Practical: the team lead should not assign a teammate to a file until the previous teammate has committed AND pushed AND another teammate has confirmed pull-clean state. "Just landed, you're cleared" is too optimistic when other teammates may have stale reads of the file.
